Origem: issue #489 (Sprint 10.5, Fase 3, plano H1), `docs/auditoria/decisoes-canvas.md` (R1 a R4, decisão 4); evidências M2, M3, M4, M37 a M42 (M46 é tratada só como conferência, ver D9). ## 1. Objetivo

Deixar as telas de acesso (login, duas etapas, código de reserva, conta travada, esqueci minha senha, nova senha, link vencido, convite novo e com conta existente, convite vencido, escolha de organização e sem acesso) iguais ao canvas em layout, textos, botões e janelas, a 1440 e 390 px, nos temas em que o canvas existe. A API ganha só dados de leitura que o canvas pede (D1, D2). As regras de acesso (RN-ACE-*) não mudam.

Fora do escopo: ativar ou gerar códigos na Minha conta (#490); mudar a regra de duas etapas (decisão 4: sem "Agora não" para o Coordenador); cadastro público e aula experimental; M46 (estado de erro de Cobranças, é da #573; aqui só se confere que o `ErrorState` base segue o canvas).

## 6. Decisões

- D1 (muda a API, só leitura): o canvas do convite mostra organização, quem convidou e unidades, e a API não tinha. Pela R2 das decisões, `InviteInfo` ganha `organizationName`, `invitedByName` e `unitNames`, só para convite pendente válido; o convite vencido não revela a organização (RN-ACE-10), então a orientação "com o nome da academia" do canvas de convite vencido vira texto sem o nome. Não contraria a especificação. Alternativa descartada: texto genérico também no convite válido, que contraria o canvas.
- D2 (muda a API e o banco, só leitura): "Último acesso" por vínculo no canvas da escolha; hoje só existe o da conta (V9). Entra `account_link.last_access_at`, gravado ao escolher o vínculo; sem acesso ainda, a linha mostra "Nunca entrou". Alternativa descartada: usar o último acesso da conta em todos os vínculos, que mostraria dado errado.
- D3: "restam N" usa a contagem de códigos de reserva não usados da conta. Suposição: se ela não puder sair antes de a senha estar conferida, a caixa mostra o texto sem número ("gere códigos novos em Minha conta"); se o número exigir rota nova, vira campo de leitura no ticket do login.
- D4: a tela de link vencido continua aparecendo depois da recusa da API (a página abre como formulário), porque validar o código antes exigiria rota nova que revela o estado do código. Alternativa descartada: nova rota de checagem, que muda o contrato sem regra pedindo.
- D5 (regra vence, visual do canvas): "Não aparece em vazamentos conhecidos" (RN-ACE-08) só o servidor sabe; no cliente a regra aparece neutra, não vira ✓ antes do envio (para não prometer o que não foi checado) e vira ✗ com a recusa. Alternativa descartada: ✓ otimista junto com as outras três.
- D6: "Lembrar esta escolha neste aparelho" guarda só o id do vínculo no `localStorage`; o servidor confere a posse e, se o vínculo não existir mais, a página volta a aparecer. É preferência do aparelho, sem regra de negócio.
- D7: o texto próprio de Financeiro (`areaUnavailable.financeText`) fica, pois o canvas `EstadoSemAcesso` o traz para Cobranças; as demais áreas usam o texto do canvas de celular e de gestão.
- D8: EscolhaOrganizacao deixa de ficar fora do teste visual: o caso entra com um login do MSW com 2 vínculos e sem vínculo ativo (cenário por flag no `Caso`, como `usuariosCanvas`).
- D9: M46 (erro de Cobranças) não é desta tela; o `ErrorState` base segue o canvas desde a #455 e a tela de Cobranças é tratada na #573. Aqui só se confere, sem alterar `states`.
- D10: sem "Agora não" para o Coordenador (decisão 4 do dono), já valendo em `TwoFactorRequiredPage`; só se confere que o texto continua certo.
- Suposição: o painel escuro da marca (a partir de 768 px) já bate com o canvas além do slogan; se a comparação a 1440 px mostrar outra diferença, vira ajuste na T2.
